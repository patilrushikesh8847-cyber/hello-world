# Northfield Hostel Management

A role-based hostel operations app with a React, TypeScript, Vite and Tailwind frontend and a FastAPI backend backed by Supabase PostgreSQL. Student, room, invoice, payment, complaint, notice and report screens read and write through the API; dashboard counts are calculated from stored records.

## Requirements

- Node.js 20+ and npm
- Python 3.11+
- A Supabase project with its PostgreSQL connection string
- `psql` or the Supabase SQL Editor for applying migrations

## Database setup

In the Supabase SQL Editor, run `backend/migrations/001_initial.sql` and then `backend/migrations/002_invoice_balances.sql`, in that order. The migrations create the relational schema, constraints, indexes and invoice balance view. Row-level security is enabled, and direct `anon`/`authenticated` table access is revoked; all application data access goes through the role-checked FastAPI service.

Copy `backend/.env.example` to `backend/.env`. Set `DATABASE_URL` to the Supabase **backend-only** PostgreSQL connection string and set `JWT_SECRET` to a newly generated secret of at least 32 characters. Do not put either secret in the frontend or commit an `.env` file. For a deployed API, use Supabase's direct connection or a session pooler; configure TLS as required by the selected connection string.

Install and start the API from PowerShell:

```powershell
Set-Location backend
py -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
uvicorn app.main:app --reload
```

Create the initial administrator using the same `DATABASE_URL` environment variable as the API:

```powershell
python seed_admin.py
```

The script prompts for credentials and stores an Argon2 password hash; it does not print or persist the plaintext password. Create later Warden accounts from **Rooms → Add warden**, then assign a warden when creating a hostel. Administrators can create student accounts from **Students → Add student**.

## Frontend setup

From the repository root, copy `.env.example` to `.env` and set `VITE_API_URL` to the API origin (the local default is `http://localhost:8000`). Set `VITE_CURRENCY` to the ISO 4217 currency used by your institution if it is not USD. Then run:

```powershell
npm ci
npm run dev
```

Open the Vite URL shown in the terminal. Production frontend bundles contain only `VITE_API_URL`, which is public configuration—not a database password, JWT signing key, service-role key, or payment credential.

## Implemented workflows

- **Authentication:** administrator, warden and student roles; Argon2 password hashes; signed, expiring bearer sessions with server-side logout revocation; one-time password reset tokens with a 30-minute expiry.
- **Students:** admin provisioning, student search, profile updates, active/inactive status, student self-service data scoping.
- **Rooms:** hostel and room creation, capacity checks, allocation/check-in, explicit check-out before a transfer, and warden assignment scoping. Room capacity is serialized in a database transaction to prevent concurrent over-allocation.
- **Fees:** invoice creation, outstanding balances derived from recorded payment rows, payment history and printable receipts. Payment entry records funds actually received; it is not a card processor and never reports a simulated gateway success.
- **Student/warden views:** students see their own room, invoices, receipts, complaints and notices; wardens see records limited to their assigned hostel.
- **Complaints and notices:** students submit and track complaints; administrators and wardens update complaint status and publish audience-scoped notices.
- **Reports:** authorized live counts, warden-scoped report data, CSV downloads and print layouts.

## Password-reset email

Configure all of `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER` (if required), `SMTP_PASSWORD` (if required), and `SMTP_FROM` in the **API** environment to send actual reset-token email. Until SMTP is configured, password reset fails explicitly with `503`; it does not claim that email was delivered. Reset tokens are one-time, hashed before storage and expire after 30 minutes.

## Deployment

### API

`render.yaml` describes a Render web service. Connect this repository, provide the Supabase `DATABASE_URL` and API `FRONTEND_ORIGINS` during deployment, and configure SMTP if password-reset email is needed. `JWT_SECRET` is generated by Render. After applying both database migrations, create the first administrator by running `python seed_admin.py` in the deployed service's shell with `DATABASE_URL` configured. Restrict database credentials to the backend and enable TLS.

Set `FRONTEND_ORIGINS` to the exact deployed frontend origin (for example `https://your-account.github.io`), not a wildcard. Include additional comma-separated origins only when needed.

### Frontend

The GitHub Actions workflow builds `dist/` and deploys it to GitHub Pages when `main` is updated. Configure the repository Actions variable `VITE_API_URL` with the public HTTPS origin of the deployed API before enabling Pages. The Vite production base path is set for this repository's `/hello-world/` project page. For a custom domain, change that base path to `/`.

### External credentials / operational limits

- A Supabase project and PostgreSQL connection string are required before the API can start.
- A JWT signing secret must be supplied to the API; never expose it to Vite.
- SMTP credentials are required for working password-reset email.
- This implementation records staff-verified cash, bank-transfer, card and other payment events. No external payment gateway is integrated, so it does not accept or process student card payments.
- Hosting requires deployment accounts/configuration for Supabase, the API host, and (if used) GitHub Pages. The application does not include demo accounts or fabricated operational records.

## API reference and checks

When the API is running, interactive OpenAPI docs are at `/docs`, and the unauthenticated health check is `/health`. Protected routes return `401` when unsigned and `403` when the signed-in role lacks permission.

```powershell
npm run build
```

No live database workflow can be verified until a Supabase project is configured; use the Supabase SQL Editor and the application API docs to verify the deployed schema and role-protected flows.
